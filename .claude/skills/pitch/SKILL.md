Write the pitch for what exists, not what was planned. Extra notes from the user: $ARGUMENTS

1. Gather facts, don't invent them: read SPEC.md and CLAUDE.md (Idea, Sponsor challenges, Deployed, Current status, Decisions), skim `git log --oneline`, and run `bash scripts/check.sh`. Anything that's broken or unfinished is left out of the demo path or named honestly as "next". Any step that calls an external API live (Gemini, a sponsor API) gets a **Backup** line: the seeded record to open instead and the exact sentence to say if the fallback fires.
2. Write `PITCH.md` with:
   - **30-second version first:** three sentences — who it's for and the problem, what it does, the one impressive thing — for the hallway, the table before the judge sits down, and the Devpost tagline. The user memorizes this one.
   - **Demo script (≤ 230 spoken words ≈ 1:50 at 130 wpm; print the word count under it):** the problem in one sentence, then the exact clicks a judge sees in order, then the one technically interesting thing under the hood, then what's next. Mark each step with what to say and what to click. Put the most impressive moment in the first 30 seconds. If a step has a wait (an API call), give the sentence to say during it. Make sure the script visibly hits all five judging criteria: Completion (show it working end to end, no "imagine this part"), Design (let the UI breathe for a beat), Technology (name the hard part in one sentence), Originality (the twist), Practicality (who uses it and how, in one line).
   - **Devpost writeup:** Inspiration, What it does, How we built it (stack + the interesting technical piece), Challenges, Accomplishments, What's next. Plain language, no hype words. Include the sponsor challenges it qualifies for and why, one line each.
   - **Disclosure line** (rules require it): "Auth, upload, deploy, CI scaffolding, and the LLM helper (`llm.py`) came from a starter template I built before the event; [project name] — [its actual features] — was built during ShellHacks." List every starter file the project's sponsor claim depends on, and name the event-time work specifically so it's clear what's new.
   - **Judge Q&A:** 5 likely questions with one-sentence answers (e.g. "what happens with bad input?", "how would this scale?", "what did the AI tools do vs. you?"). Answer the AI one in this shape: what the tools wrote / what you decided (demo path, data model, cuts) / what you debugged yourself.
3. Keep it tight: the whole file under 120 lines. The user will read it out loud, so short sentences.
   Also rewrite the top of `README.md` for the project (judges click the repo link): name, one-paragraph description, the live Vercel URL from CLAUDE.md → Deployed (ask if blank) with a "run `seed.py <render-url>` before judging — every deploy wipes the demo data" note beside it, a screenshot, how to run it locally, and the disclosure line. Move the starter-kit notes below it under "Development". Set `<title>` and add a `<meta name="description">` in `frontend/index.html` to the project's name and one-liner — that's what shows in the browser tab and in link previews.
4. Screenshots for Devpost and the README: use the `webapp-testing` skill (Python Playwright) to save `docs/screenshots/01-<screen>.png` … for the 3–4 screens in the demo script, at 1280×800 with real demo data on screen (run `backend/seed.py` first if the data is missing). Check where every image in the seed data and UI came from — anything not the user's own goes in CREDITS.md with a visible credit in the UI, or `/ship-check` fails on it. Its server helper works with this stack exactly like this — note the backslashes: `with_server.py` runs its `--server` strings through cmd.exe, where `venv/Scripts/python` fails (in the Bash tool the forward-slash form is fine):
   `python <path-to-webapp-testing>/scripts/with_server.py --server 'cd backend && venv\Scripts\python -m uvicorn main:app --port 8000' --port 8000 --server 'cd frontend && npm run dev' --port 5173 -- python shots.py`
   If the dev servers are already running, skip the helper and just run the Playwright script. Reference the screenshots from README.md.
5. Tell the user to time themselves reading the script once — if it's over 2 minutes, cut the "what's next" section first — and to memorize the 30-second version.
